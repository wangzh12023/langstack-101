# 未定义行为与抽象机

C 与 C++ 等语言的语义建立在 **抽象机** 上：标准描述在这种机器上哪些操作有确定结果，哪些属于未定义行为（undefined behavior, UB）、未指定或实现定义。编译器在「程序不触发 UB」的假定下做变换。真实 CPU 上「碰巧能跑」只说明这一次的机器状态，不构成对抽象机命题的反驳。

## 抽象机与具体机器

抽象机规定求值顺序约束、对象生命周期、指针指称的对象等。编译器把抽象机程序翻译成具体 ISA 上的指令序列，并允许在不改变任何**有定义**执行的可观察行为的前提下改写程序（as-if 规则）。一旦源程序存在 UB，标准不再约束该执行的任何结果：可以崩溃，可以「正常」算完，也可以被优化删掉你以为存在的检查。

## 有符号溢出与检查消失

在 C 里，`int` 上的有符号溢出是 UB。于是对类似

```c
int f(int x) {
  if (x + 1 > x)
    return 1;
  return 0;
}
```

编译器可以假定 `x+1` 永不溢出，从而把条件当成恒真或按代数规则简化，生成的代码里可能看不到你写的那次比较。把 `x` 改成无符号类型后，回绕有定义，同一段源码的优化空间就不同。口试里常用这个问题区分「机器上的补码加法」与「语言里的有符号加法」。

## 常见 UB 类别（轮廓）

下列每一类都值得在 C/C++ 分论里落到例子，这里先定版图：

- 非法指针：空指针解引用、悬空指针、越界访问
- 别名与生命周期：违反有效类型 / 严格别名假定、使用已结束生命周期的对象
- 有符号整数溢出、移位越界等算术规则
- 数据竞争（C++ 等对数据竞争直接定义为 UB）

Rust 在安全子集里把许多同类问题拒在编译期；`unsafe` 块把责任交回程序员，其契约仍接近「不要留下语言层面的 UB」。托管语言用运行时检查或内存模型把一部分问题变成异常或有定义的竞争语义，但本地代码与 FFI 边界仍可能重新引入无定义空间。

## 与口试的对应

被问到「为什么编译器可以删掉防御性检查」时，先指明该检查所依赖的运算在抽象机里是否有定义；再说明 as-if 优化如何在「假定 UB 不发生」下重写控制流。用具体机器上的一次运行结果反驳优化合法性，会在这一层被拆穿。
