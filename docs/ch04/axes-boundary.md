# 并发、对象、正确性边界与 FFI

另外几条轴决定并发下的可见性与同步、对象与派发在内存中的形状、抽象机里的未定义行为，以及跨语言调用时要对齐的约定。

### 操作系统线程

一对一映射到内核线程（或近似）。共享地址空间，同步靠互斥锁、条件变量、原子操作。上下文切换与栈内存成本由内核与运行时共同承担。C/C++/Rust 的原生线程、Java 的平台线程属于此路。

### 用户态调度与 M:N

Go 的 goroutine、部分 Erlang/Java 虚拟线程实现把大量轻量任务多路复用到较少的 OS 线程上。阻塞点（I/O、channel、停车场）由运行时切入调度器。对话时要分清：语言里的「线程」是内核实体还是可让出的用户态任务。

### async / await 状态机

编译器把异步函数切成状态机：遇 `await` 挂起并返回轮询/可完成对象，完成后续跑。执行仍落在某种执行器（线程池、事件循环）上。Rust `Future`、C#/JS/Python asyncio、Kotlin 协程同属「语法糖 + 状态机 + 执行器」结构；取消、本地线程亲和与 `Send` 一类约束因语言而异。

### CSP 与 actor

CSP 风格用 channel 传递消息，降低共享内存频率（Go channel、部分 CSP 库）。Actor 把状态封在邮箱后面的串行处理里（Erlang/Akka）。两者仍可能在运行时内部用共享内存实现；模型约束的是**程序员默认可见的共享方式**。

### 数据竞争与竞态条件

**数据竞争**（定义随语言而变）：冲突的并发内存访问，且缺少语言认可的同步；C++ 把数据竞争定为 UB，Java 则另有 JMM 下的有定义但可能令人惊讶的行为。**竞态条件**更宽：结果依赖调度时序，即使每次访问都有同步，逻辑仍可能错。讨论锁与 `atomic` 时先对齐谈的是哪一个。

内存序关键字（`memory_order_*`、`volatile` 在 Java 与 C 中含义不同）是在语言层把 [硬件内存序](../ch01/memory-ordering.md) 收成可移植契约；不会自动消除业务层的竞态。

运行时里一个「对象」在内存中的字节布局，决定了字段访问成本、对齐填充、以及派发元数据放在哪里。派发机制见 [派发机制与胖指针](polymorphism-repr.md)；本页先固定头与载荷。

### 标量与聚合

机器字、浮点、指针按 ABI 对齐放置。结构体按字段顺序（或语言规定的重排规则）排布，中间插入 padding 以满足对齐；末尾也可能 pad 以便放进数组时对齐。C 的 `sizeof`/`alignof`、Rust 的 `size_of`/`align_of` 直接反映布局。跨 FFI 传递结构体时，两边填充规则必须一致。

### 对象头

托管运行时常在用户字段前加 **对象头**：类型指针或类型 ID、GC 标记位、锁/哈希位、数组长度等。HotSpot 的 mark word + class pointer（压缩 oops 下更窄）、Go 的类型信息、CPython 的 `PyObject_HEAD`（引用计数与类型指针）都是头的变体。头的宽度影响缓存行利用率与「小对象」成本。

### 数组与字符串

长度可放在头里（JVM 数组）、旁边的胖指针里（Rust 切片）、或哨兵/显式字段里（C 字符串）。越界检查是否存在，决定加载元素是一拍还是「比较 + 分支 + 加载」。

### 装箱与内联

值类型/原始类型可内联在栈或聚合内；变成接口/Object/`Any` 时往往 **装箱** 到堆上带对象头的包装里。泛型擦除语言里，装箱是常见隐藏分配源。逃逸分析或标量替换若成功，又可以把堆分配变回寄存器/栈上的裸值——基准数字会随优化是否触发而跳变。

### 与 GC、RC 的交界

追踪式 GC 依赖头里或并行位图中的标记，以及写屏障对指针字段写入的拦截，见 [追踪式 GC 机制轮廓](gc-mechanics.md)。引用计数则把计数放在头里或旁边，赋值路径改计数。布局讨论与回收讨论共用「头里有什么」这一问。

多态调用的成本取决于：目标地址是否在编译期已知，以及对象旁边还要带多少元数据。下面并排三种常见形态。

### C++ 虚调用

带虚函数的对象通常在对象头附近存放 **虚表指针（vptr）**。调用 `p->f()` 时：加载 vptr → 在 vtable 固定偏移取函数指针 → 间接 `call`。单次调用至少一次额外负载与一次间接跳转；多重继承与虚继承还会加 thunk 与调整 `this` 的偏移。

### Go interface

`interface` 值在实现上可视为「类型信息 + 数据指针」（具体布局随版本优化，对话讲两字段模型即可）。调用接口方法：从类型信息找到方法表 → 间接调用。把具体值赋给接口可能分配并装箱到堆上，使看起来像「值传递」的路径产生分配。

### Rust `dyn Trait`

`&dyn Trait` / `Box<dyn Trait>` 是 **胖指针**：数据指针 + 指向 vtable 的指针（vtable 含方法与尺寸/对齐等）。调用通过 vtable 间接完成。与 Go 类似是「指针+表」；与 C++ 的差异是：C++ vptr 往往存在对象内部，Rust 的 fat pointer 把表指针放在引用一侧，对象本身可以保持朴素布局。

```mermaid
flowchart LR
  subgraph cpp [C++ 对象]
    VP[vptr] --> VT[vtable]
    VT --> F[f()]
  end
  subgraph rust [Rust dyn]
    DATA[data ptr]
    VT2[vtable ptr] --> M[method]
  end
```

### 并排计数间接层

| 形态 | 引用/对象上多带什么 | 一次方法调用典型路径 |
| --- | --- | --- |
| C++ 虚函数 | 对象内 vptr | load vptr → load 函数指针 → indirect call；`this` 已在对象里 |
| Go interface | 接口值：类型信息 + 数据指针 | 从类型信息取方法地址 → indirect call；具体值可能已装箱 |
| Rust `dyn Trait` | 胖指针：data + vtable | 从胖指针第二字取 vtable → load 方法 → indirect call |

C++ 把派发指针存在对象头侧；Rust 把 vtable 指针存在引用侧，对象可为朴素布局（便于嵌入与 FFI）。Go 的接口值本身就是双字，赋值给接口的转换成本要单独算。对象头里还有哪些字段见 [对象表示与运行时布局](object-layout.md)。

### 静态派发对照

模板/泛型单态化、`final`、去虚化分析成功时，调用可变成直接 `call` 甚至内联，间接层消失。讨论「零成本抽象」时，要问最终是否还留下 vptr 负载；讨论 JS 引擎时，内联缓存（IC）用另一套机制把「看似动态」的调用在稳态下打到近直连路径——见 JavaScript 分论。

C 与 C++ 等语言的语义建立在 **抽象机** 上：标准描述在这种机器上哪些操作有确定结果，哪些属于未定义行为（undefined behavior, UB）、未指定或实现定义。编译器在「程序不触发 UB」的假定下做变换。真实 CPU 上「碰巧能跑」只说明这一次的机器状态，不构成对抽象机命题的反驳。

### 抽象机与具体机器

抽象机规定求值顺序约束、对象生命周期、指针指称的对象等。编译器把抽象机程序翻译成具体 ISA 上的指令序列，并允许在不改变任何**有定义**执行的可观察行为的前提下改写程序（as-if 规则）。一旦源程序存在 UB，标准不再约束该执行的任何结果：可以崩溃，可以「正常」算完，也可以被优化删掉你以为存在的检查。

### 有符号溢出与检查消失

在 C 里，`int` 上的有符号溢出是 UB。于是对类似

```c
int f(int x) {
  if (x + 1 > x)
    return 1;
  return 0;
}
```

编译器可以假定 `x+1` 永不溢出，从而把条件当成恒真或按代数规则简化，生成的代码里可能看不到你写的那次比较。把 `x` 改成无符号类型后，回绕有定义，同一段源码的优化空间就不同。口试里常用这个问题区分「机器上的补码加法」与「语言里的有符号加法」。

### 常见 UB 类别（轮廓）

下列每一类都值得在 C/C++ 分论里落到例子，这里先定版图：

- 非法指针：空指针解引用、悬空指针、越界访问
- 别名与生命周期：违反有效类型 / 严格别名假定、使用已结束生命周期的对象
- 有符号整数溢出、移位越界等算术规则
- 数据竞争（C++ 等对数据竞争直接定义为 UB）

Rust 在安全子集里把许多同类问题拒在编译期；`unsafe` 块把责任交回程序员，其契约仍接近「不要留下语言层面的 UB」。托管语言用运行时检查或内存模型把一部分问题变成异常或有定义的竞争语义，但本地代码与 FFI 边界仍可能重新引入无定义空间。

### 与口试的对应

被问到「为什么编译器可以删掉防御性检查」时，先指明该检查所依赖的运算在抽象机里是否有定义；再说明 as-if 优化如何在「假定 UB 不发生」下重写控制流。用具体机器上的一次运行结果反驳优化合法性，会在这一层被拆穿。

外语函数接口（FFI）把两种语言的调用接到同一条机器调用约定上。失败通常不是「语法翻译错了」，而是 ABI、所有权、异常与线程模型在边界上不一致。

### 调用约定与符号

两侧必须就下列事项达成一致：参数与返回值占用哪些寄存器/栈槽、结构体如何拆分或经隐藏指针返回、栈对齐、名称修饰（`extern "C"` 去掉 C++ mangling）。Linux x86-64 上与 C 互操作时，默认对齐 [System V AMD64 ABI](../ch02/sysv-amd64-abi.md)。写错一个整数参数位置，表现为「读到垃圾」而不是链接失败。

动态库还要保证符号可见性与依赖库装载顺序；`dlopen` / 绑定方式见 [位置无关代码与动态链接](../ch02/pic-dynamic.md)。

### 所有权与寿命

谁分配、谁释放、指针能活多久，必须在边界上显式约定。常见模式：调用方分配、被调方写入；被调方分配、调用方按对方规则释放（`free`、`CoTaskMemFree`、语言专用 dealloc）；或只借用不转移所有权（只读借用跨越调用期间保持存活）。Rust 的 `unsafe` FFI、Go 的 `cgo`、JVM/JNI 的局部/全局引用，都是在把这套契约编码成 API。

把托管对象的内部指针传给可能持有它的 C 代码，却未钉住（pin）或延长寿命，会在 GC 搬迁或收集后变成悬空指针。

### 异常、panic 与 errno

C 的错误多用返回值与 `errno`。C++ 异常、Rust panic、Java 异常不能安全地穿越未约定的外语栈帧：中间帧缺少匹配的展开表或人格（personality），会导致终止或破坏状态。跨边界要么换成错误码，要么保证整条栈都由同一种展开 ABI 建成。

### 表示与线程

结构体填充、端序、回调的线程（是否在持有锁时调用、是否要求主线程）同属 FFI 表面。Go 调用 C 可能阻塞 OS 线程；JNI 要求按线程附加 JVM。基准里「一层 FFI 包装」的成本往往来自编组（marshalling）、拷贝与线程切换，而不只是一次 `call`。

语言分论页会写该语言默认 FFI 工具链与典型陷阱；本页只固定跨语言都会问到的边界问题。
