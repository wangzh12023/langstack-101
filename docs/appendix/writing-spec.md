# 编写规范

本站正文统一遵守下列规则。审稿与改写时按条目核对；违反任一条即改，不另开例外讨论。

## 标题

1. 标题用陈述句概括本节主题，不用问句。写「System V AMD64 ABI」，不写「什么是 System V ABI？」。
2. 同级标题共用一条分类轴。组成、改进路线、设计理由不要并列在同一级。
3. 标题不堆术语清单。写「Linux 启动流程」，不写「Linux 启动流程：UEFI、Bootloader、Kernel、Initramfs、systemd」。覆盖范围放在标题下第一段。
4. 标题不做吸睛文案，不用强硬比喻或悬念句。

## 强调与预告

5. 不在讲解前贴重要性标签。「必知」「很重要」「我觉得挺重要」一律删掉；重要与否由内容本身体现。
6. 不写发言预告和动机解释。「我想分享几个看法」「我并不是建议你……而是希望你……」整段删除，直接进入内容。
7. 不用主观表述替读者揣测情绪，不擅自转向学习方法或心态劝告。

## 否定与防御

8. 不为想象中的误解补防御性说明。读者没有提出的误解，不必先排除；真正需要区分的概念，直接陈述两边是什么。
9. 删除正确的废话过渡。「……并不完全一致」若后面没有具体差异，整句删；有差异就直接写差异。

## 结构与节奏

10. 避免把连贯解释切成一串短确认段。能用一段写清的推理，不要拆成多次停顿。
11. 同一信息只讲一遍。换位置、换包装、末尾再「一句话总结」而无新信息的，删掉重复。
12. 分类说明不要反复套同一短标签模板。需要并列时用完整句子或表格，不要通篇「甲：…… / 乙：……」节拍。

## 公式与代码

13. 短关系、数值结果、符号用行内公式；多步推导、较长表达式、矩阵、需编号引用的关键公式用行间公式。不因含有数学符号就另起一行，不加 `\boxed{}` 做强调。

## 卡片与装饰

14. Admonition（`note` / `tip` / `warning` / `info` / `example`）用于补充边界、实验步骤、易混对照，不用于重复正文结论。
15. 图标与 SVG 优先使用已入库的 Simple Icons / Material / Twemoji，不手绘装饰图。
16. Mermaid 图只画正文将引用的结构；图下用一两句说明读图顺序，不把图当装饰。

## 语言分论页骨架

语言分论页按同一骨架组织，便于对照，但仍写成连贯叙述，不把骨架标签抄成小标题堆：

- 实现谱系与执行管线
- 内存与对象表示
- 并发与运行时调度
- 与 C / ABI 的边界
- 影响正确性与性能的语义
- 导师对话笔记（该语言常被追问的点，写事实不写励志）

## 审稿检查表

- [ ] 标题均为陈述式，且兄弟标题同轴
- [ ] 无重要性前置、无悬念文案、无情绪揣测
- [ ] 无空过渡、无换皮重复、无防御性否定堆砌
- [ ] 短公式行内；admonition 不重复结论
- [ ] 关键术语可回链到术语表或首次定义页
