# 编写规范

本站要同时满足两件事：读起来像一条能跟住的技术叙事；又避开常见的技术写作噪音。二者冲突时，**可读的叙事优先**，用下面的细则约束噪音，而不是把正文削成词条列表。

## 整书怎么写，而不是每页套模板

全书只有一条主问题：**一段程序文本如何变成 CPU 上可讨论的行为，以及各语言在这条路上插入了哪些机制。**

章节存在是因为读者在这条路上还缺某一截，不是因为还有一个术语没被单独建页。目录保持短；细节进正文。不要给每一页固定「背景 / 目标 / 小结 / 导师笔记」栏目——需要动机时，把「缺了什么就走不动下一步」写进段首即可。

语言分论尤其如此：按该语言真正特殊的地方组织，不必六节骨架齐套；与别的语言相同的机制回链共性章，不要重讲。

## 标题

1. 用陈述句概括本节在整条路径上的角色，不用问句。
2. 同级标题共用一条分类轴（时间顺序、抽象层次、或同一对象的侧面），不要把「组成 / 理由 / 路线」混在同一级。
3. 标题不堆术语清单；覆盖范围用标题下第一段话说清。
4. 不用悬念文案或强硬比喻当标题。

## 禁止的噪音（不是禁止技术动机）

5. 不在讲解前贴「必知 / 很重要」。
6. 不写作者元叙述：「我想分享」「我并不是建议你……而是希望……」。
7. 不揣测读者情绪，不改写成学法/心态劝告。
8. 不为假想误解做防御性排雷；需要区分的概念，直接写清两边各是什么。
9. 删空过渡（「并不完全一致」后面却没有差异）。
10. 同一事实不换包装重讲；没有新信息的「一句话总结」删掉。
11. 少用「短标签：一句」铺满全页；能写成段落就写段落。
12. 少把推理切成一串确认句小段。

**允许且需要写的：** 这个机制解决机器或工具链上的哪件具体事、若不建立它后文哪一步会悬空。那是技术上下文，不是写作预告。

## 公式与装饰

13. 短关系用行内公式；长推导才用行间公式；不加 `\boxed{}`。
14. Admonition 放实验步骤或窄边界，不重复正文结论。
15. 图标用现成库；Mermaid 只画正文要引用的结构。

## 审稿时多问一句

除检查是否触发上面的噪音外，再问：读者读完这一节，是否更清楚自己在整条「源码 → 进程 → 语言差异」路上的位置？若只是多背了几个互不串联的词，这一节还没写到。
