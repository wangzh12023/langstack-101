# 内核边界上的接口

除用户态函数调用和链接装载外，程序还会通过系统调用进入内核，使用线程局部存储，用原子指令同步内存可见性，并在信号送达时看到另一套栈帧。C/C++ 里偶尔会嵌入内联汇编。这些接口与调用约定、装载过程相关，但各自有独立规则。

对自写汇编：先确认调用号与参数寄存器，再单步看 `%rax` 返回值。系统调用号表以平台 `unistd_64.h` 或 `ausyscall` 为准；本站示例只用稳定的小数目编号（`read`/`write`/`exit`）。

TLS 为每个线程提供一份独立的变量副本：同一符号名，不同线程读到不同地址上的值。实现依赖编译器生成的访问序列、链接器留下的 TLS 重定位，以及运行时（动态链接器 / libc）在线程创建时分配的块。本页给出 x86-64 System V 上常见的访问形态；通用线程与内存序问题见第一章与 [原子指令](atomics-x86.md)。

### 模型与段寄存器

在 x86-64 Linux 上，线程本地数据常以 `%fs`（有时文档亦提 `%gs`，用户态 TLS 基址惯例是 `%fs`）为基址访问。硬件把段基址设为当前线程的 TLS 块相关地址；指令里的位移选中块内字段：

```asm
    movq    %fs:0xfffffffffffffffc, %rax   # 示意：相对 TLS 基的偏移
```

C11 的 `_Thread_local` / gcc 的 `__thread` 变量由编译器改写成上述一类序列。初始可执行映像与每个 `dlopen` 的模块可以贡献自己的 TLS 模板；线程创建时按模板复制或清零出每线程实例。

### 通用动态与局部执行

ABI 定义了多种 TLS 访问模型，按「是否已知模块、是否可把偏移当成常量」递降开销：

| 模型 | 典型场景 | 特征 |
| --- | --- | --- |
| General Dynamic (GD) | 共享库中、跨模块 | 经 `__tls_get_addr`，两次间接 |
| Local Dynamic (LD) | 同一模块内多个 TLS 变量 | 一次取模块基，再加偏移 |
| Initial Exec (IE) | 主程序，或已知在启动时已装载的模块 | GOT 中放 TLS 偏移，经 `%fs` 访问 |
| Local Exec (LE) | 可执行文件内、静态可知 | 直接 `%fs:offset`，开销最低 |

`-ftls-model=` 与是否 `-fPIC`、是否静态链接，决定编译器选哪一档。读反汇编时看到对 `__tls_get_addr` 的调用，说明落在 GD/LD；只见 `%fs:` 与 GOT 槽，多半是 IE/LE。

### 与栈、errno 的关系

`errno` 在现代 libc 中是 TLS 变量：每个线程一份，避免多线程下互相覆盖。信号处理器里调用非异步信号安全的函数，可能与主控制流交错改写同一线程的 TLS 状态——这是信号安全规则的来源之一，细节见 [信号](exceptions-signals.md)。

栈本身也是每线程一份，但栈不是 TLS 变量：它由线程创建时的栈映射提供，通过 `%rsp` 寻址，不走 `%fs` 相对的 TLS 模板。

### 检视

```bash
readelf -r foo.o | grep -i tls
objdump -d foo.o
```

TLS 相关重定位类型名中常带 `TLS`（如 `R_X86_64_TLSGD`、`R_X86_64_TPOFF32`）。把重定位类型、生成的指令序列与上表模型对齐，即可判断该变量在当前链接方式下的访问代价。

多线程下，普通 `mov`/`add` 不保证「读改写」对其他核表现为一步，也不自动提供跨线程的发布/获取语义。x86-64 用带 `lock` 前缀的读改写、`xchg`，以及 `mfence`/`lfence`/`sfence` 等栅栏表达这些约束。语言层的 `memory_order` 最终要落到这类指令或对其省略的证明上；硬件序的直觉见 [存储缓冲与内存序](../ch01/memory-ordering.md)。

### LOCK 前缀与读改写

`lock` 前缀作用于后随的读改写内存指令，使该操作在缓存一致性协议下对其他观察者表现为原子：

```asm
    lock addq $1, (%rdi)
    lock cmpxchgq %rsi, (%rdi)
    lock xaddq %rax, (%rdi)
```

`xchg` 与内存操作数搭配时，即使不写 `lock` 也有锁总线/锁缓存行语义。`cmpxchg` 比较 `%rax` 与目的内存：相等则写入源寄存器值并置 `ZF`，否则把内存旧值装入 `%rax` 并清 `ZF`——CAS 循环的底座。

无 `lock` 的普通 `addq $1, (%rdi)` 在单线程语义下正确，在并发计数上可能丢失更新。

### 内存序指令

x86-64 对普通用户态存储/加载提供较强的总存储序（TSO）外观：商店缓冲仍允许「自己的读看到自己未引退的写」等局部效应，但对多数编程模型已比弱序架构少补栅栏。显式栅栏仍出现在：

```asm
    mfence                  # 全栅栏：读写均不可跨越
    lfence
    sfence
```

编译器为 C++/`std::atomic` 的 `seq_cst` 存储等可能插入 `mfence` 或改用 `xchg`；`acquire`/`release` 在 x86 上常仅靠普通加载/存储加编译器屏障即可，因为硬件已禁止多数乱序组合。把「语言序」等同于「一定生成 mfence」会误判 `-O2` 输出。

### 与编译器屏障的分工

内联汇编里的 `memory` clobber 阻止编译器跨过该语句重排对内存的缓存假设，但不生成 CPU 栅栏。CPU 栅栏阻止其他核对访问的可见性重排。两者都需要时，既要 `volatile`/atomic 语义或 `memory` clobber，又要 `mfence` 一类指令（或等价的 `lock` 操作）。扩展语法见 [内联汇编](inline-asm.md)。

### 阅读练习

对一段含 `std::atomic::fetch_add` 的 C++，分别编译：

```bash
clang++ -O2 -S -o - atom.cpp | sed -n '1,80p'
```

核对是否出现 `lock`、是否出现 `mfence`，并对照所选 `memory_order`。同一源码在 AArch64 上通常看到更多显式栅栏——对照可用于理解「硬件默认序」与「语言序」的分工，而不要求本页平行展开第二套 ISA。

同步异常（除零、缺页、非法指令）与异步信号（`SIGINT`、定时器、对端关闭）都会打断当前指令流。内核把控制转到处理路径时，用户态看到的是信号处理器或被重启的系统调用，而不是普通的 `call`。本页只建立与汇编/栈阅读相关的模型；POSIX 信号语义的完备手册不在此展开。

### 同步陷阱与异步信号

**同步**：当前指令触发故障或陷阱，例如 `#PF`（缺页）、`#DE`（除零）。内核决定是补页后恢复、向进程投递信号（如 `SIGSEGV`、`SIGFPE`），还是终止进程。

**异步**：与当前指令无直接因果关系，例如 `kill`、终端产生的 `SIGINT`、`SIGALRM`。内核在返回用户态的合适边界投递。

两者最终都可能以「进入用户态信号处理器」的形式出现；处理器函数的 ABI 与普通 C 函数相近，但可调用集合受**异步信号安全**限制。

### 信号帧

投递到用户态处理器时，内核在线程栈上（或备用信号栈上）构造**信号帧**：保存被打断时的寄存器映像、信号编号、`siginfo` 等，再把用户 `%rip` 指到处理器入口。处理器返回应使用 `sigreturn`（经 libc 包装），由内核根据帧恢复原上下文。

因此，在处理器里看到的 `%rsp` 往往不是「业务函数 prologue 之后」的位置；调试器若按普通帧链回溯，可能多出一帧 `[signal trampoline]`。手写汇编若在红区存放活数据，需确认信号到达时内核不会践踏——SysV 红区约定要求信号处理路径避开对红区的破坏；依赖红区的叶函数在「可能被信号打断且处理器也用红区」的组合下仍需谨慎。

### 与调试、errno 的交界

`-O2` 下断点「对不上行号」主要来自指令调度与槽位复用；信号帧则是另一类「栈上看起来多了一截」的来源。`errno` 为 TLS：处理器里调用不安全的库函数，可能弄脏主控制流正在解读的 `errno`。规则收成一句：信号处理器中只调用文档标明 async-signal-safe 的接口，或仅设 `volatile sig_atomic_t` 标志、把实质工作留给主循环。

### 与系统调用的关系

阻塞在 `syscall` 上的线程收到信号时，内核可选择：用 `-EINTR` 中断调用并进入处理器；或（若设置了 `SA_RESTART` 一类行为）在处理器返回后重启调用。用户代码若看到 `errno == EINTR`，对应前者。这与「`call` 被信号打断」不同：`call` 目标仍是用户态地址，信号帧叠在同一用户栈上；`syscall` 路径多一次进出内核的边界。

### 阅读路径

对仍活着的进程：

```bash
cat /proc/self/status | grep Sig
## SigPnd / SigBlk / SigIgn / SigCgt
```

对带处理器的小程序，在处理器入口设断点，向上回溯应能看到信号 trampoline 与被打断的用户帧。把该帧与 [栈帧](stack-frames.md) 里的普通 prologue 对照，可以分清「业务调用」与「内核代建的异步帧」。硬件故障何时变成信号、何时变成杀进程，以具体 `si_code` 与内核策略为准；本页不把每种 `#xx` 异常枚举成表。

GCC/Clang 的扩展内联汇编把汇编模板嵌进 C/C++，并用约束字符串告诉编译器：哪些操作数是输入/输出、允许落在什么寄存器或内存、以及该语句破坏了哪些寄存器或内存假设。写错约束等于对优化器撒谎，表现为「高优化等级下结果随机错误」。本页给出阅读与书写所需的最小模型。

### 基本语法

```c
asm volatile (
    "addq %1, %0"
    : "+r"(x)           /* 输出：读写，任意通用寄存器 */
    : "r"(y)            /* 输入 */
    : /* clobbers */
);
```

冒号分三段：**输出**、**输入**、**破坏列表**。模板里 `%0`、`%1` 按操作数出现顺序编号；AT&T 语法下操作数仍是源在前、目的在后，与站内汇编一致。`volatile` 阻止编译器在「看起来没有数据依赖」时删除或过度下移该语句；对有副作用（`syscall`、写端口、内存栅栏）的片段通常需要。

### 常用约束

| 约束 | 含义 |
| --- | --- |
| `r` | 通用寄存器 |
| `m` | 内存操作数 |
| `i` | 整型立即数 |
| `0`、`1`… | 与第 n 个操作数同一位置（早期写法；现多用 `+`） |
| `=r` | 只写寄存器输出 |
| `+r` | 读写寄存器 |

x86 特化字母（`a`=`%rax`、`D`=`%rdi` 等）用于必须固定寄存器的指令（`syscall`、`cpuid`、`rdtsc`）。能写宽约束时不要无故核对寄存器，以免增加寄存器压力。

### 破坏列表与 memory

```c
asm volatile ("syscall"
    : "=a"(ret)
    : "a"(nr), "D"(arg0), "S"(arg1)
    : "rcx", "r11", "memory");
```

`syscall` 由硬件使用 `%rcx`/`%r11`，必须列入 clobber。`"memory"` 表示该语句可能读写任意内存：编译器不得跨过它缓存内存值到寄存器——这是**编译器屏障**，不是 CPU `mfence`。需要硬件序时，另写栅栏指令或使用 `std::atomic`，见 [原子指令](atomics-x86.md)。

### 与单独 .s 文件的选择

短、必须与周围 C 变量交互、且依赖编译器分配寄存器时，用内联汇编。大段逻辑、要单测的例程、或需要完整 prologue 的函数，放进独立 `.s`，经 [SysV ABI](sysv-amd64-abi.md) 与 C 互调更清晰。内联汇编的输出在 `-O0` 与 `-O2` 下寄存器编号可变，读 `clang -S` 时以约束语义为准，不要把某次分配当成 ABI 保证。
