# 整数与浮点

`int`、`double`、以及 Python 的任意精度整数，最终都表现为固定宽度的比特运算，或软件实现的大数算法。同一条「加一」在基准里可能是一次寄存器加法，也可能伴随一次堆分配。

### 二进制与位宽

\(n\) 位无符号整数表示 \(\{0,1,\ldots,2^n-1\}\)。常见宽度：8（字节）、16、32、64；指针宽度由 ABI 决定，本站主线 x86-64 上用户态指针为 64 位（实际规范地址更窄，见 [虚拟内存与页表](virtual-memory.md)）。同一比特串按无符号或有符号解释，数值不同；按不同宽度截断或零扩展/符号扩展，结果也不同。

用 8 位举例：比特 `1111_1110` 作无符号是 \(254\)；作有符号补码是 \(-2\)。语言若把「看起来像正数的字面量」塞进有符号窄类型，或在移位时混用符号扩展与逻辑移位，源码层的直觉会和机器层分叉。

### 补码

现代通用 CPU 与主流语言对有符号整数采用**二元补码**（two's complement）。正数与同宽度无符号编码相同；负数 \(x\)（\(x<0\)）编码为 \(2^n - |x|\) 的低 \(n\) 位，等价于按位取反再加一。补码使加法器无需区分符号：同一套加法电路覆盖有符号与无符号加法，溢出只是模 \(2^n\) 的环绕。

取值范围：\(n\) 位有符号为 \([-2^{n-1},\,2^{n-1}-1]\)。8 位为 \([-128,127]\)；`-128` 的补码是 `1000_0000`，对其取负在位宽内无法表示，这是补码的结构性质，不是实现疏忽。

减法实现为加上加数的补码。比较有符号大小时，不能直接当无符号比大小；CPU 用符号标志与溢出标志组合，或专用有符号比较条件码。语言里写 `a < b`，编译器会选有符号或无符号比较指令，类型签不签名决定选哪条。

有符号溢出在 C/C++ 抽象机中是未定义行为：编译器可假定「有符号加法永不溢出」而删掉看起来在防溢出的检查。机器上补码环绕仍然发生，因此「我机器上溢出后变成负数」不能反驳「标准允许删检查」。Rust 在 debug 下溢出默认 panic，release 下环绕；Java 的 `int`/`long` 固定环绕；这些是语言契约差异，底层仍是同一套补码加法。细节与 UB 的关系在第四章展开。补码环绕是硬件事实，语言是否承认溢出结果是另一层。

### 端序

多字节整数在内存中按字节排列。**小端**（little-endian）把最低有效字节放在最低地址；**大端**相反。x86-64 与 AArch64 在常规数据上均以小端为主（AArch64 可配置，通用 OS 部署为小端）。寄存器内部没有「端序」问题——端序描述的是**内存中的字节序**。

例：32 位值 `0x12345678` 在小端内存中从低地址起为 `78 56 34 12`。网络协议、文件格式、部分二进制协议常用大端；读写时需显式转换。用指针把 `uint32_t` 缓冲区强转成字节数组观察时，看到的顺序就是端序；用移位 `((x>>8)&0xff)` 取「次低字节」则与端序无关，因为移位在数值语义上操作。

结构体里多字段的布局还涉及对齐与填充，那是 ABI 与对象布局问题；端序只回答「单个多字节标量在内存中的字节方向」。

### 移位与掩码

逻辑左移 `<< k` 在无符号语义下等价于乘 \(2^k\)（在位宽内）。逻辑右移填 0；算术右移对有符号数复制符号位，使 `-2 >> 1` 仍为 `-1`（在算术右移语义下）。C 对有符号数的右移是否算术由实现定义；Java 用 `>>` 算术、`>>>` 逻辑；Rust 对有符号用算术右移。写可移植位运算时，先固定类型有无符号，再选移位种类。

掩码用按位与取出字段：`(x >> s) & ((1<<w)-1)` 取出从位 `s` 起宽 `w` 的字段。按位或合并字段；按位异或翻转。对齐向下：`x & ~((1<<a)-1)`（`a` 为对齐的 log2）。这些模式在页表项、ELF 旗标、指令编码解码里反复出现。

移位计数若大于等于位宽，C 中行为未定义；硬件上 x86 对掩码移位计数有自己的规则（例如 32 位数移位计数掩成 5 位）。语言与硬件再次可能不一致：可移植代码应保证移位量在 \([0,n-1]\)。

### 语言整数类型的落点

| 语言/类型 | 宽度 | 溢出 | 与机器的关系 |
| --- | --- | --- | --- |
| C `int` / `long` | 实现定义（LP64 下 `int` 32、`long` 64） | 有符号溢出 UB | 直接对应通用寄存器宽度上的补码运算 |
| C 定宽 `int32_t` 等 | 固定 | 同上 | 跨平台 ABI 与序列化更稳妥 |
| Rust `i32`/`u32`/`i64`… | 固定 | debug 检查 / release 环绕（可改） | 与 LLVM 整数类型对齐 |
| Java `int`/`long` | 32/64 固定 | 环绕 | 字节码再由 JIT 降到机器补码 |
| Python `int` | 任意精度 | 不溢出（内存耗尽除外） | 小整数可能走机器字快速路径，大整数进堆对象 |
| JavaScript `Number` | IEEE 754 binary64 | 非整数语义 | 「整数」仅在安全整数范围内可精确表示 |
| Go `int` | 与指针同宽 | 环绕 | 另有 `int32`/`int64` 定宽 |

跨语言基准里同一个「fib(n)」：C/Rust 用 `uint64` 会在 \(n\) 较大时环绕；Python 自动变大整数，运算变成堆分配与大数算法；JS 若用 `Number`，超过 \(2^{53}-1\) 后连整数都不精确。比较耗时时，先对齐「算的是不是同一种整数」，再谈编译器与 GC。

指针与 `size_t`/`usize` 通常与地址宽度一致，用于下标与对象大小。把指针差值塞进 32 位有符号类型、或在 64 位地址上用 32 位下标假设「数组够小」，属于类型宽度错误，不是算法错误。

符号扩展与零扩展在调用约定与窄类型提升里反复出现：把 `int8_t` 的 `-1`（`0xff`）扩展到 32 位，符号扩展得 `0xffffffff`，零扩展得 `0x000000ff`。C 的整数提升、Rust 的 `as` 转换、Java 的加宽运算，都在选这两种之一。混用「字节当无符号长度」与「字节当有符号字符」是协议解析里的经典缺陷源。

!!! example "口头核对"

    给定比特 `0b1111_1111`（8 位）：无符号 \(255\)，有符号 \(-1\)。`-1` 加 `1` 得 `0`，与无符号 `255+1` 模 256 环绕同为 `0`——补码加法电路合一。再问：C 里有符号 `char` 从 `127` 再加一是否「必须」变成 `-128`？按标准是 UB；按机器补码常见结果是 `-128`。两句话都要说得出。

整数是模运算世界里的精确值（在位宽内）。浮点用舍入换动态范围；结合律不再成立，所以「同一公式」在并行归约后比特不一致，不一定是实现写错。

浮点把实数映到有限位模式，用「科学计数法」换动态范围：相近的小数能区分，极大或极小的数靠放大指数表示。IEEE 754 规定了二进制格式、舍入、特殊值与例外；主流 CPU 与语言的 `float`/`double` 都落在这套标准上。整数补码是精确的模运算；浮点运算每一步都可能舍入，结合律与分配律不再成立。

### IEEE 754 二进制格式

常用两种：binary32（单精度，`float`）与 binary64（双精度，`double`）。布局均为：1 位符号、\(E\) 位指数、\(M\) 位尾数（小数域）。binary32：\(E=8\)，\(M=23\)；binary64：\(E=11\)，\(M=52\)。指数用偏移码（bias）：binary32 的 bias 为 \(127\)，binary64 为 \(1023\)。规格化数的值可写为

\[
(-1)^s \times (1.m)_2 \times 2^{e-\mathrm{bias}}
\]

其中 \(m\) 是尾数比特给出的小数部分；隐藏的前导 `1` 不占存储。全零指数表示非规格化数与零；全一指数表示无穷与 NaN。符号位使 \(+0\) 与 \(-0\) 可区分，比较时通常视为相等。

精确可表示的数是离散集合。例如 binary64 在 \(1\) 附近，相邻两数间距（单位舍入 ulp）为 \(2^{-52}\)；到 \(2^{53}\) 量级，间距变为 \(2\)，奇数整数已无法精确表示。这直接解释了 JavaScript `Number`（即 binary64）的「安全整数」上界 \(2^{53}-1\)：超出后「整数运算」也会丢精度。

### 舍入

默认舍入模式多为**就近偶数**（round to nearest, ties to even）：结果落在两可表示数正中间时，选最低有效位为 0 的那一侧，避免统计偏差。其他模式包括向零、向 \(+\infty\)、向 \(-\infty\)；数值库与部分语言可改舍入，但应用代码极少改全局模式。向零舍入与整数截断直觉接近，却会在累加中引入系统偏差；就近偶数是默认的原因之一。

一次加减乘除：先按无限精度算精确数学结果，再按当前模式舍入到目标格式。因此 `0.1 + 0.2` 在 binary64 里通常不等于 `0.3` 的字面表示——字面量 `0.1` 本身已是对实数 \(1/10\) 的近似。比较浮点应用容差或整数化后的精确路径，而不是依赖 `==` 在十进制直觉上成立。十进制字符串格式化再解析，还会叠上另一层舍入，调试时应用十六进制浮点格式（如 C 的 `%a`）看真实比特。

融合乘加（FMA）一次乘加只舍入一次，结果可与「先乘后加、两次舍入」不同。编译器在许可（如 `-ffast-math` 或显式 FMA）下改写表达式时，数值会变；基准若对位要求可复现，需固定是否允许 FMA。硬件提供 FMA 端口时，吞吐与延迟曲线也与标量乘加不同，性能对比要固定同一类指令。

### 结合律失效

实数加法满足 \((a+b)+c = a+(b+c)\)。浮点加法不满足：大数加小数时，小数可能被吞掉。经典例子：令 \(a=10^{16}\)，\(b=-10^{16}\)，\(c=1.0\)（binary64）。则 `(a+b)+c` 得 `1.0`，而 `a+(b+c)` 得 `0.0`，因为 `b+c` 在 \(10^{16}\) 量级下仍是 \(b\)。并行归约、改变循环展开顺序、向量化重排加法树，都会改变结果比特，即使算法「数学上」相同。

乘法与加混合时，分配律同样失效。优化器若启用「快速数学」假设（忽略 NaN/Inf、重联想、消除多余舍入），可生成更快但数值不同的代码。语言默认是否允许这类变换不同：Fortran 传统上较松；C/C++ 默认较严，靠旗标放松；Java 对浮点重排限制更严以换可复现性。读基准时，同一语言不同编译旗标也可能让 float 核函数的结果与周期一起变。

### 特殊值与谓词

除以零（在浮点语义下）可产生 \(\pm\infty\)；无效运算产生 NaN。NaN 与任何值（含自身）的相等比较为假，故 `x == x` 可用于探测 NaN。有序比较与无序比较在指令集上分家（如 x86 的 `ucomisd` vs `comisd`）；语言里的 `<` 对 NaN 的行为需查规范。刷新（flush-to-zero）与非规格化数缓慢处理是微架构细节：大量非规格化运算会拖慢数值核，有时被误读成「算法变慢」。

误差分析在工程上常用 ulp 或相对误差，而不是「小数点后几位」。两次舍入的复合运算，最坏误差可大于单次 0.5 ulp；长链累加用 Kahan 补偿或更高精度累加器，是在接受 IEEE 运算的前提下减小发散，而不是恢复实数结合律。库函数（`sin`、`exp`、`pow`）的 ulp 误差界与是否保证正确舍入，属于 libm 契约，与硬件加减乘除的 IEEE 保证分层：后者由 CPU/FPU 落实，前者由软件近似。

### 基准里的浮点路径

跨语言「同一算法」若实际类型不同，数字不可横比：

- 一侧用 `double` 累加，另一侧用 `float` 或定点数，既改精度又改吞吐（SIMD 宽度、端口压力不同）。
- 一侧用整数算 fib，一侧因语言默认 `Number`/`float` 走浮点，比较的是不同功能单元与不同舍入。
- 归约顺序被并行或向量化改写，校验和比特不一致时，需区分「实现错误」与「合法重联想」。
- JIT 语言在 warmup 前后可能从解释态的软浮点/装箱，切到标量或 SIMD 机器浮点，墙钟时间含编译与去优化。

读性能数字时，先确认：类型宽度、是否允许 `-ffast-math` 同类选项、是否测到了 NaN/非规格化边界、归约是否要求确定性。整数路径的环绕与 UB 见 [比特与整数编码](bits-integers.md)；此处对应的是舍入与重排。

SIMD 路径把多个 float/double 打进向量寄存器，吞吐上升，但水平归约的树形加法再次引入结合顺序选择；「标量结果」与「向量结果」比特不一致时，先查是否允许重联想，再查是否有 bug。混合精度（用 `float` 算、用 `double` 累加）在深度学习与科学计算里常见，基准标题若只写「同一公式」而不写类型，排名无意义。

!!! note "与整数的对照"

    整数：位宽内运算可精确，溢出是环绕或 UB。浮点：几乎每次运算都可能舍入，溢出趋向 \(\pm\infty\)，下溢趋向零或非规格化。两者都是有限表示；失败模式不同，不能共用同一套「对不对」的口头标准。
